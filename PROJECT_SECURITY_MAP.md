## Architecture

```
Browser
  │  cookie: session (httpOnly, secure=prod, sameSite=lax)
  ▼
Next.js 16 (App Router, RSC + API routes) — single Node process
  │
  ├─ (auth) route group: /login /signup — no session required
  ├─ (app) route group: layout.tsx calls requireUser() → redirect /login
  │     edge-level gating via src/proxy.ts (Next.js 16 renamed "middleware.ts"
│     to "proxy.ts" — same convention, different file name; missed in the
│     first pass of this audit, corrected here)
  ├─ /api/* route handlers — EACH authenticated route calls getSession()
  │     independently (no shared middleware-level auth). Public exceptions:
  │     /api/stripe/webhook (HMAC-signature-verified instead, no session),
  │     and the pre-auth routes under /api/auth/* (login, signup,
  │     verify-email, resend-verification — a session doesn't exist yet)
  │
  ▼
Drizzle ORM → postgres.js → Postgres (Neon/Supabase/Docker, or local PGlite dev)
  │
  ├─ users, sessions, subscriptions, imports, bank_connections,
  │  checkout_sessions, stripe_events
  ▼
External services (server-side only, all via env-gated optional clients):
  - Anthropic API (AI_MODEL, ANTHROPIC_API_KEY) — quick-add parsing, insight narration
  - Stripe (Payment Link + webhook + Billing Portal) — STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET
  - Plaid (bank import) — PLAID_CLIENT_ID/SECRET
  - TrueLayer (bank import, OAuth2) — TRUELAYER_CLIENT_ID/SECRET
```

**Stack**: Next.js 16 (App Router, Turbopack), React 19, TypeScript, Tailwind v4, Drizzle ORM, Postgres, Zod validation, Vitest, argon2, framer-motion.

**CORRECTION (post-Phase-3 E2E testing found this was wrong):** `src/proxy.ts` **does** provide a centralized edge-level gate — Next.js 16 renamed the "middleware.ts" convention to "proxy.ts", which this repo's first audit pass missed (searched for the old filename). It does three things on every request: (1) redirects to `/login` for protected-prefix paths with no session cookie present (cheap, cookie-presence only — `requireUser()` remains the authoritative check); (2) rejects cross-origin state-changing requests that carry the session cookie (Origin/Referer vs. Host comparison — see the CSRF note below); (3) issues a nonce-based `Content-Security-Policy` header with `strict-dynamic` script-src. Route protection is layered: proxy.ts (edge) → `requireUser()`/`getSession()` (authoritative, per-page/per-route) — not just the latter alone as originally reported.

**Real bug found in this file via E2E testing (fixed in Phase 4):** the CSRF check compared `Origin`/`Referer` against `request.nextUrl.origin`, which does not reliably reflect the actual incoming `Host` header (observed empirically: resolved to `localhost` while the real Host/Origin was `127.0.0.1`) — this silently 403'd every legitimate same-origin mutation, including logout, whenever the app was reached via anything other than literally "localhost". Fixed to compare against the raw `Host` header instead. See `PRODUCTION_READINESS_REPORT.md` for details.

**CI/CD (added in the production-readiness phase — see `PRODUCTION_READINESS_REPORT.md` §8):** `.github/workflows/ci.yml` runs lint/typecheck/unit-and-integration-tests/build plus a separate Playwright E2E job on every push/PR against `main`; `codeql.yml` runs CodeQL static analysis; a `secret-scan` job runs gitleaks; a `dependency-audit` job runs `scripts/check-npm-audit.mjs` (baseline-diffed `npm audit`, fails only on a *new* high/critical finding — see `npm-audit-baseline.json`). Branch protection requiring these checks still needs to be enabled manually in GitHub's repo Settings (not settable from a workflow file) — see the production-readiness report's deployment checklist.

## Trust boundaries

| Boundary | Mechanism |
|---|---|
| Browser ↔ Server | Session cookie (opaque random token, httpOnly, sameSite=lax, secure in prod). DB stores only sha256(token), never the raw token. |
| Server ↔ Postgres | `postgres.js`, `prepare:false`, parameterized via Drizzle (no raw SQL string interpolation found). |
| Server ↔ Anthropic/Stripe/Plaid/TrueLayer | Server-only env secrets; each has an `isXConfigured()` gate — absent key = feature disabled, not a crash. |
| Stripe → Server | Webhook signature verification (`STRIPE_WEBHOOK_SECRET`) — confirmed in `stripe-webhook.ts`. |
| TrueLayer → Server | OAuth2 authorization-code redirect + CSRF state cookie, verified in callback route. |

## Sensitive data locations

- `users.passwordHash` — argon2id, never selected into `SafeUser`/`getSession()` result.
- `sessions.tokenHash` — sha256 of session token; raw token lives only in the httpOnly cookie.
- `bank_connections.accessTokenEncrypted` / `refreshTokenEncrypted` — AES-256-GCM via `TOKEN_ENCRYPTION_KEY` (`src/lib/security/token-encryption.ts`), IV+authTag+ciphertext, base64.
- `.env` — gitignored, confirmed not tracked (`git ls-files` shows only `.env.example`, which contains no real values).
- No secrets found in tracked files (checked for `sk-`, `sk_live_`, AKIA, ghp_, xox*, PEM private key headers — zero matches).

## Attack surfaces (routes accepting untrusted input)

- `/api/auth/{signup,login,logout,verify-email,resend-verification}` — public, rate-limited (distributed where configured — see Known gaps below).
- `/api/subscriptions`, `/api/subscriptions/[id]`, `/api/subscriptions/quick-add` — authenticated, ownership-scoped (`WHERE userId = session.user.id AND id = :id` pattern, confirmed in `[id]/route.ts`).
- `/api/imports/*` (analyze, confirm, history, plaid/*, truelayer/*) — authenticated + rate-limited; file upload paths validate type/size before parsing.
- `/api/stripe/webhook` — public but signature-verified; no session required by design.
- `/api/billing/{activate,portal}`, `/api/ai/narrate-insights`, `/api/me` — authenticated.

## Known gaps (see audit report for severity/plan)

Status as of the production-readiness phase (see `SECURITY_HARDENING_REPORT.md` Phase 3, `PRODUCTION_READINESS_REPORT.md`, `FINAL_PRODUCTION_AUDIT.md`) — items below are what's *actually still open*, not the original Phase-1 list verbatim:

1. ~~No email verification~~ — **implemented**: signup issues a single-use, hashed, 24h-TTL token; login is blocked until verified. See `src/lib/auth/email-verification.ts`.
2. ~~No account lockout~~ — **implemented**: DB-backed progressive lockout (`login_attempts` table, `src/lib/auth/lockout.ts`) on top of the in-memory IP+email/per-email/per-IP rate limits (10/15min IP+email, 20/hr per-email, 30/15min per-IP).
3. **Rate limiting is only partially distributed.** The 4 highest-value auth endpoints (login, signup, verify-email, resend-verification) support an Upstash-Redis-backed distributed limiter with in-memory fallback (`src/lib/rate-limit-distributed.ts`); every other limiter (billing, imports, AI, subscriptions, profile-update — all already behind an authenticated session) stays in-memory-per-process, a deliberate, documented scope decision.
4. No password reset flow exists at all (not a regression — never built).
5. ~~No CI/CD~~ — **implemented**: see the CI/CD correction above this section.
6. No RBAC — single implicit "user" role; `plan` (free/pro) is entitlement, not authorization role. No admin/support/moderator surface exists in the app today, so RBAC has nothing to attach to yet.
7. Signup's `email_taken` 409 confirms account existence for a taken email — a pre-existing, deliberately-not-fixed enumeration vector (see `SECURITY_HARDENING_REPORT.md` Phase 3's own note on this).
